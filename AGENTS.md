# AGENTS.md

## Purpose

This file contains repository-level instructions for coding agents working on Dokumentverkstad.

Follow these instructions when inspecting, modifying, testing, or extending the codebase. More specific task instructions may supplement these rules, but should not silently override the architectural principles below.

## Project overview

Dokumentverkstad is a personal document and knowledge-processing system.

The system ingests source documents, processes them in the background, and creates structured knowledge objects derived from those sources.

The project is designed to remain understandable, maintainable, and suitable for self-hosting. Avoid unnecessary infrastructure, dependencies, and architectural complexity.

## Core domain concepts

The main knowledge object types are:

* Summary
* Claim
* Insight
* Question

Knowledge objects may be generated by AI or created by a human.

Source precision is a core principle. Knowledge derived from a source should remain traceable to the relevant source material whenever the data model and source format allow it.

Preserve the existing meaning of domain concepts. Do not rename or redefine them as part of unrelated work.

## Architecture

The application has distinct responsibilities for:

* the web application;
* the background worker;
* the CLI;
* persistence and domain logic;
* document and AI processing.

Preserve these boundaries unless a task explicitly requires an architectural change.

### Web application

The web process should handle interactive requests and return promptly.

Do not perform long-running AI calls, document processing, or other expensive background work synchronously inside web requests.

### Background worker

Long-running document processing and AI operations should normally be delegated to the background worker.

Do not create parallel processing paths when an operation belongs in the existing worker pipeline.

### CLI

CLI commands should reuse the same application and domain logic as the rest of the system where appropriate.

Avoid implementing separate versions of existing behaviour solely for CLI use.

### Configuration

Use environment-based configuration where appropriate.

Do not hard-code deployment-specific paths, credentials, secrets, hosts, or other environment-specific values.

The application must remain suitable for running on a Linux/VPS environment.

## Ingest and document processing

Uploaded, manually created, or discovered sources should enter the normal ingest and processing architecture where applicable.

Do not assume that ingesting a source and processing it are the same operation.

Avoid creating special-case processing paths unless the source type genuinely requires different behaviour.

Processing should be repeatable and predictable. Avoid unnecessary reprocessing when usable results already exist unless regeneration is explicitly requested.

## AI processing

AI calls should normally run asynchronously through the worker.

Keep model-specific behaviour and prompts separate from core domain logic where practical.

Do not make core application behaviour unnecessarily dependent on a particular AI model or provider.

Avoid unnecessary AI calls. Reuse existing results when appropriate rather than regenerating equivalent content.

AI-generated knowledge should preserve available source provenance and source precision.

## Development principles

When modifying the project:

1. Inspect the relevant existing code before making changes.
2. Understand the current architecture and conventions.
3. Reuse existing abstractions and patterns where appropriate.
4. Make the smallest coherent change that solves the requested problem.
5. Preserve existing architecture unless the task explicitly requires changing it.
6. Do not introduce new dependencies without a clear reason.
7. Do not silently change data models, persistence formats, or public interfaces.
8. Maintain backward compatibility unless the task explicitly requires otherwise.
9. Add or update tests for changed behaviour.
10. Prefer clear, explicit code over unnecessary abstraction.

## Scope discipline

Implement the requested change with the smallest coherent modification to the existing system.

Do not perform unrelated refactoring, rename existing concepts, or introduce abstractions solely for anticipated future requirements.

Do not redesign working parts of the system merely because another architecture or pattern might also be reasonable.

Prefer the project's existing patterns over introducing a different pattern solely because it is more familiar or generally considered preferable.

If you discover an unrelated problem while working on a task, report it rather than fixing it unless the fix is necessary to complete the requested change safely.

If a requested change appears to require a substantial architectural change, identify that explicitly before treating the architectural change as incidental implementation work.

## Dependencies

Prefer the Python standard library and existing project dependencies when they are sufficient.

Before adding a dependency:

1. Check whether the project already has functionality that solves the problem.
2. Consider whether the standard library is sufficient.
3. Add the dependency only if it provides a meaningful advantage over a simple local implementation.

Do not introduce infrastructure services solely for convenience when the existing architecture can reasonably handle the requirement.

## Persistence and data models

Treat persisted data and existing data models as stable interfaces.

Do not:

* rename persisted fields casually;
* change field semantics as part of unrelated work;
* discard existing data;
* introduce incompatible schema changes without explicit justification;
* assume that existing stored data can simply be regenerated.

When a schema or persistence change is genuinely required, make the compatibility and migration implications explicit.

## Performance

Avoid unnecessary:

* database queries;
* repeated parsing;
* repeated file access;
* AI calls;
* recomputation of existing results.

Prefer fixing identifiable performance problems over introducing speculative caching or complexity.

Document listing and rendering performance are areas where unnecessary work should be treated with particular care.

## Error handling

Failures should be visible and diagnosable.

Do not silently swallow exceptions merely to keep a process running.

Handle expected failure modes explicitly where appropriate and preserve enough context to diagnose unexpected failures.

Background jobs should fail in a way that makes the failed operation identifiable rather than leaving ambiguous partial state.

## Testing

Run relevant tests after making changes.

Run the complete test suite before considering a code change complete.

Existing tests should continue to pass unless the requested change intentionally changes the behaviour they describe.

When fixing a bug, add a regression test when the behaviour can reasonably be tested.

When adding new behaviour, add tests at the appropriate level rather than relying solely on manual verification.

Do not modify tests merely to make an incorrect implementation pass.

If a test cannot be run or remains failing, report that explicitly.

## Verification

After implementing a change:

1. Review the resulting diff for unintended changes.
2. Run the relevant tests.
3. Run the complete test suite.
4. Verify the requested behaviour directly when feasible.
5. Report what changed.
6. Report the tests and verification performed.
7. Report unresolved issues, limitations, or architectural implications.

Do not claim that something works unless it has been verified to the extent reasonably possible.

## Code quality

Follow the style and conventions already present in the repository.

Use names that reflect existing project terminology.

Keep functions and modules focused on clear responsibilities.

Comments should explain non-obvious reasoning, constraints, or decisions rather than restating the code.

Avoid speculative generalization. A straightforward implementation for a known requirement is preferable to a framework for hypothetical future requirements.

## Security and secrets

Never commit credentials, API keys, tokens, passwords, or other secrets.

Do not expose secrets through logs, error messages, generated files, or test fixtures.

Use the project's configuration mechanisms for sensitive values.

Treat source documents and generated knowledge as potentially private data.

## Documentation

Update documentation when a change affects documented behaviour, setup, configuration, architecture, or user-facing workflows.

Do not duplicate extensive documentation in this file. `AGENTS.md` defines how agents should work in the repository; other documentation should explain the system itself and its current functionality.

## General rule

When uncertain, prefer preserving existing behaviour and architecture over making a broader change.

Understand first, change second.

Make the smallest change that fully solves the requested problem, test it, and report clearly what was done.
